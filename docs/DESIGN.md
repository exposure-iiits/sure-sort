# PhotoCull architecture

SureSort is the project; **PhotoCull** is the desktop application's name. C++17, Qt 6.8 Widgets, CMake, and dynamically linked LibRaw ≥0.21. The following viewer architecture was implemented in Phase 1; automatic output processing is described below. Originals are never modified.

`Photo` contains a stable path-derived ID and source-file list. `FolderScanner` recursively enumerates the selected directory and its subfolders on its own single-thread pool, filters extensions, groups RAW+JPEG stems case-insensitively within each containing directory, and sorts with numeric QCollator plus a deterministic tie-break. IDs use the containing directory rather than the selected root, preserving existing IDs and allowing the same photo to be opened from a parent folder. Results carry a folder epoch. Standalone PNGs remain separate from RAW/JPEG groups. Directory symlinks are not followed. Moved-photo recovery includes original source paths anywhere under the selected directory.

`ImageDecoder` is UI-independent and returns QImage plus oriented source dimensions, errors, and preview provenance. JPEG/PNG use reader scaling and automatic EXIF transforms. RAW uses one heap-owned LibRaw per job, ranks JPEG thumbnails by oriented fit size, tries alternatives including bitmap thumbnails, and applies LibRaw flip only when original embedded EXIF is absent. Foreground fit loads can half-size-develop as a last resort; prefetch and detail loads never do. Known ICC profiles become sRGB. All intermediate LibRaw buffers have RAII deleters.

`PreviewController` owns catalog, generation/epoch, three-thread decode pool, bounded pending requests, and `ImageCache`. On navigation it replaces pending work, cancels obsolete running work cooperatively, and checks generation again at delivery. It schedules foreground first, detail second, and up to two background prefetches at a time after foreground completion (up to four ahead and two behind, following navigation direction and cache capacity). Matching running preview work can satisfy the newest generation without duplicate decoding. Qt image reads are not forcibly interruptible; old jobs retain at most three pool slots until they return. LibRaw progress callback supports cooperative cancellation. Folder switches never synchronously drain: tokens invalidate running jobs and epoch guards discard results. Shutdown cancels and drains after GUI event-loop exit; workers never wait for GUI callbacks.

`ImageCache` is a GUI-thread-only hash + list LRU keyed by photo ID and physical display target. Cost is `QImage::sizeInBytes()`, default 256 MiB, configurable by CLI. Images exceeding budget are displayed without admission. Only display-target-sized images enter it. Full-detail images bypass cache, are discarded on fit/navigation, and remain only for the current zoomed photo. RAW detail means largest usable embedded preview, never sensor development.

`PhotoViewer`, a custom QWidget, paints one QImage with QPainter; this avoids scene/pixmap copies and graphics-item machinery for a single rectangular image. Image coordinates, zoom and pan are independent of decode resolution. 100% maps one source pixel to one device pixel. Cursor-anchored wheel zoom and drag pan operate in logical coordinates. A 120 ms resize debounce requests the new viewport × DPR; screen/DPI changes use the same route. Preview remains visible during detail load and resizing.

`MainWindow` connects UI and controllers. `ShortcutManager` maps sequences to named actions and tracks held keys with a chord-binding API; JSON configuration can later populate those APIs. Focus loss clears held state. Phase 2 supplies destination digit/custom bindings. Watermark settings and immutable assets live outside the viewer; it paints a supplied snapshot.

Qt Test exercises actual scanning, EXIF generation, color, targets, byte eviction, injected delayed decodes, cancellation, and stale delivery. A release benchmark tool records scan/decode/cache timings; real-camera RAW and monitor/DPI checks remain explicit manual gates. Native MSVC/Qt deployment uses official Qt plus vcpkg x64-windows dynamic libraries.

## Phase 2 — automatic processing on assignment

`DestinationDialog` edits ordered mappings; `ShortcutManager` validates conflicts and installs assignment bindings with auto-repeat disabled. `SortingController` stores assignments separately from `Photo`, emits auto-advance after a durable assignment transaction, and dispatches tasks to a separate single-thread, low-priority QThreadPool. Queued tasks do not retain decoded photographs; Phase 3 shares an immutable logo asset. Preview workers never perform output processing or wait for it.

`ProcessingPipeline` loads originals. Unedited JPEG/PNG with watermarking disabled and default output settings use byte copies; RAW and RAW+JPEG use a separate full-sensor LibRaw instance with `half_size=0`, camera WB, quality demosaicing, oriented sRGB output and configurable JPEG encoding. Phase 4 applies shared tone, rotation and crop after decoding/development; watermark composition follows geometry and precedes encoding. RAW processing never calls the embedded-preview loader.

`SessionStore` uses Qt SQL/SQLite schema version 5, WAL and FULL synchronization. Small GUI-thread transactions journal configuration, immutable source/destination/edit/watermark/output task snapshots, assignment references, undo history and debounced browsing position. Photograph I/O, hashing and development stay on the worker. QLockFile excludes a second writer to the same session; a newer schema is refused. Persistence failure disables processing rather than publishing unjournaled files.

Tasks progress queued → processing → prepared → completed, or failed/cancelled. The worker writes a unique same-directory `.part`, syncs it, computes SHA-256/file identity, and returns. The GUI commits prepared metadata **before** publication. Windows uses no-replace MoveFileExW; POSIX uses a same-filesystem no-replace link. Publication collision fails safely and can be retried. Restart recognizes a renamed output from its prepared journal instead of generating duplicates. Interrupted pre-journal partials have no proven ownership, so are preserved and new temps used.

Undo/reassignment retires the prior task and cancels its token. Late results are cleaned before the next processing job, never attached to the new assignment. Windows cleanup opens a handle denying other writers/deletion, checks identity, timestamps, size and contents, then deletes through the same handle. Changed/replaced/in-use outputs are preserved and reported. The unverified POSIX path conservatively preserves outputs because advisory locking cannot provide the same guarantee. Config changes apply to future assignments; undo restores the former destination snapshot even if its mapping was removed.

Closing cancels/drains after the event loop; durable unfinished work resumes next launch. The internal cancellation API leaves jobs stopped; the interface uses Ctrl+Z/clear/reassignment. Folder switches affect browsing only, so assigned jobs continue. RAW development is limited to one job and a 1 GiB LibRaw raw-memory limit; total memory includes other buffers/cache. Supported EXIF transfer and output preferences are described below; advanced development controls remain future work.

## Phase 3 — shared watermark rendering

`watermark.*` has no Widgets dependency. It validates settings, decodes bounded PNG assets into premultiplied sRGB, computes relative rectangles, and paints with smooth SourceOver compositing and PNG alpha × slider opacity. Logo size means longest logo edge / shorter photograph side; padding uses that same photograph side. One fit constraint preserves aspect ratio and both margins. `paintWatermark` serves the viewer and the full-resolution `compositeWatermark` path.

`PhotoViewer` paints the unchanged preview/detail image, then the logo inside its existing `imageRect()`. The photo rectangle already includes fit, zoom, pan and DPI behavior, so the overlay stays attached to the image rather than the widget bounds. No composited photograph enters the cache. `WatermarkDialog` is a compact modeless control window with four corners and no secondary preview or Apply/Export action. Controls emit instantly; PNG reads/decode use a separate bounded import worker.

`SortingController` owns the current snapshot and debounces settings persistence by 150 ms, flushing on normal shutdown. Assignments durably capture settings plus SHA-256 PNG version in the same transaction as the task. `watermark_assets` stores encoded bytes once per version, independent of the imported filename. Pending jobs share immutable decoded assets; terminal task history retains settings/IDs and releases decoded asset references. A weak cache lets restart/retry/undo hydrate one required version rather than loading every historical logo. Recovery hydration runs once per uncached version on the controller thread; import and photograph rendering remain on workers.

SQLite v1→v2 migration adds two task columns with disabled-watermark defaults and the asset table; previous assignments/outputs remain intact. Retry and undo restore saved snapshots, including settings from before later global changes. A corrupt/missing enabled asset fails a task before publication; corrupt settings fail session load rather than silently omitting watermarks. The current missing logo can be replaced or disabled. Existing prepared-output recovery and ownership checks are reused unchanged.

Watermarked JPEGs are decoded at original resolution with automatic orientation, converted to sRGB and re-encoded at the selected JPEG quality. RAW development produces the final oriented sensor image before compositing. Standalone PNG preserves its format and alpha. Re-encoding transfers the supported EXIF subset; orientation is baked and sRGB tagged. Unknown/vendor metadata and IPTC/XMP are omitted. A camera's embedded preview may differ in crop/color from developed RAW, while watermark geometry always follows the actual displayed/output photo boundaries.

## Phase 4 — edits and interactive crop

`PhotoEdits` is a parameter value associated with Photo ID: EV tenths, five signed tone/saturation controls, clockwise quarter turns and an original-relative normalized crop. Coordinates refer to the full image after EXIF orientation, before user rotation. `rotatedNormalizedRect`, `editCropPixels` and `editedSize` handle transforms and final pixel rounding. Strict JSON validation rejects malformed snapshots instead of silently producing unedited outputs.

`renderEdits` contains the shared UI-independent adjustment engine. A 256-entry lookup table combines linear-light EV gain with display-referred brightness, contrast and smooth highlight/shadow weighting. Integer saturation uses rounded Rec.709 luminance; straight color channels preserve alpha. Full output then rotates by exact quarter turns and copies the mapped crop before watermarking. No source file is changed.

The viewer retains original preview/detail buffers and paints crop/rotation through cheap transforms, sharing geometry with output. A separate one-thread tone pool has one latest pending request, row-level cancellation and generation guards. Interactive tone work is capped at two megapixels; a 220 ms idle timer requests full-quality refinement from the same decoded image. Resizing/rotation/crop never demand full RAW sensor development. Edited buffers stay outside the original LRU and are released on photo change. Peak memory includes originals, current edited display, active processing and refinement buffers beyond the cache budget.

Crop mode temporarily displays the full rotated photograph. Mouse coordinates invert the current image rectangle into normalized coordinates; draft selection, corner handles, aspect constraints, dimming and watermark placement use that same rectangle. Middle/Alt-drag panning and wheel zoom leave normalized coordinates unchanged. Confirmation inversely rotates the draft into original coordinates; cancellation restores the committed crop. A crop request during image loading waits for the preview. Navigation/assignment are suppressed during a draft.

`EditPanel` is a collapsible, scrollable side panel. `EditShortcutsDialog` configures every editing action through `ShortcutManager`; repeated chords precede navigation, while destination repeat suppression remains. Conflicts reject plain navigation/destination keys, duplicate combinations and used hold keys. Existing destination mappings take priority over newly introduced editing defaults. Shortcuts and per-photo edits persist in SQLite.

Edits debounce for 350 ms and flush before assignment/shutdown. Task snapshots remain immutable. When a sorted photo changes, a background refresh keeps its saved destination and captures current watermark settings. A running assignment finishes its captured edits, then schedules the latest photo state. Explicit cancellation stays stopped until reassigned. Undo restores prior edit and watermark snapshots.

For a refresh, predecessor path/hash/identity are captured in the assignment transaction; the old record becomes superseded. Cleanup of its temporary files leaves the previous output in place. The new image is developed, edited, encoded, synced and fingerprinted first. If the predecessor still matches on Windows, the prepared journal records its existing final path. Publication revalidates/removes only that owned file, then performs the existing no-overwrite rename and fingerprints the published file. Changed predecessors are preserved and use a free filename; failures before publication retain the previous completed output.

Recovery distinguishes the predecessor from the new image using hash and file ID, including the predecessor-deleted/published crash boundaries. Publication/recovery tolerates creation-time changes caused by filename tunneling only when file ID, last-write, length and SHA-256 still match; normal deletion remains a full-identity, same-handle check. Schema 3 adds task edits/predecessor ownership, per-photo edits and shortcut metadata. Existing v1/v2 jobs retain their snapshots with identity edits by default.


## Phase 5 — output quality and bounded metadata

`OutputSettings` captures JPEG quality (95 default), percentage dimensions (100/75/50) and metadata preservation (default on). Schema 4 adds strict JSON task snapshots plus current preferences. Retry/Undo use the captured settings; later explicit assignment/edit refresh captures current preferences. Default unedited JPEG/PNG retains the copy path; changes requiring new pixels/encoding or metadata stripping use the processing path. Final order: original decode/full sensor development → shared tone → rotation/crop → watermark at full cropped dimensions → smooth resize → encode. Preview and output share edit/watermark math; embedded camera previews are not a promise of pixel-identical RAW development.

LibRaw uses full sensor data, camera WB with its automatic fallback, the camera matrix, AHD where applicable and explicit sRGB gamma (1/2.4, toe 12.92). Auto-bright clipping threshold is 0.001 rather than the dcraw default 0.01; no extra denoise/sharpen/highlight reconstruction passes are enabled. The foreground half-size RAW fallback uses the same transfer curve/threshold; thumbnail browsing stays fast. A separately allocated processed LibRaw bitmap is transferred to QImage with a cleanup callback, allowing sensor/demosaicing buffers to be released before editing and avoiding a full bitmap copy. Only one output worker can develop RAW; the 1 GiB limit applies to LibRaw raw buffers, not total process memory.

`ExifMetadata` reads a bounded standard-tag subset from JPEG APP1, PNG eXIf and TIFF-based RAW. LibRaw supplies basic camera/exposure/lens fallback fields for other RAW containers. Rebuilt little-endian IFDs preserve eligible capture/author/GPS fields, normalize orientation/dimensions/sRGB and omit thumbnails, structural pointers, MakerNotes and unknown tags. Individual values are limited to 4 KiB, aggregate copied values to 48 KiB and directories to 512 entries. Encoded JPEG/PNG streams pass through `MetadataDevice`, inserting APP1/eXIf without buffering or rewriting the entire encoded file. Malformed/unsupported metadata is skipped; image decoding still determines job success. Disabling metadata strips original text/EXIF while keeping color information needed for display.

The existing single-worker journal/publish/recovery machinery is reused. Status counts reflect current assignments: completed, processing/prepared, queued and failed. Reimporting a valid watermark version repairs a damaged asset row; ordinary task persistence checks asset existence without repeatedly reading PNG blobs on the GUI thread.


## Sure Sort workflow update — 18 October 2026

Schema 5 stores per-folder Copy/Move actions, immutable task operation IDs, a composite `(photo_id, category_id)` placement key and action-specific Undo history. Existing destinations migrate to Copy; legacy history is reconstructed by walking prior tasks backward. Copies in different folders coexist. Automatic refresh/retry shares the logical operation ID; manual actions get a new one. Clear affects the latest placement, and Ctrl+Z reverses one placement action without deleting unrelated copies.

Move publishes the normal processed output before relocating original bytes into `destination/Originals`. `SourceMover` runs in the existing one-worker pool with its own short-lived SQLite connection (FULL synchronization; file I/O outside transactions). Each source and reverse transfer progresses planned → prepared → published → complete: unique temporary file, flush/sync, SHA-256 and file identity, durable prepared state, no-overwrite publication, durable published state, verified source removal and transactional location update. Source removal holds the verified backup open while denying writers/deletion; original modification times are copied where supported. Unjournaled partials are preserved. Undo performs the same staged transfer back, refuses occupied/changed paths and updates ownership for preceding moves. Cleanup restores originals before deleting generated outputs, and pending chained restores resume in reverse physical move order. Restoration conflicts receive bounded automatic retries and then remain visible; restart recovery checks unfinished original restorations again. Windows handle locking is required for deletion; other platforms preserve files.

`source_locations` resolves logical original paths for processing and preview jobs; original paths remain in immutable task/history records. Moved photos are merged into source-folder catalogs and naturally sorted, including partially moved RAW+JPEG pairs. Failed stale preview requests retry if the resolved path changed. Full-resolution decoding, editing, watermarking, output preferences and bounded pools remain unchanged. Z toggles actual-size/Fit; all editing keyboard steps are five stored units (0.5 EV exposure). Original crop ratio is a dynamic ratio of the oriented full image, following user rotation and photo changes.


Schema 6 adds `automatic_retries` (0–2) and `retry_operation` to each task. One GUI timer schedules nonblocking 1/3-second delays while the existing serial worker executes prepare, verified recovery/publication, original relocation or undo cleanup. Retries retain task IDs, history, edits, watermark version and output preferences; they do not read new global settings. Publication collisions journal a free path before publishing the already prepared image. Retry counts survive restart; failed processing does not restart indefinitely. Retiring/undoing a job removes its delayed retry, and explicit cancellation never restarts processing. Original restoration retries keep reverse move order and ownership checks. Exhaustion produces an inline error and full details through the processing status control.
